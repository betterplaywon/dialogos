# 화면과 서버

판정 실험의 엔진을 붙인 토론 화면과 서버입니다. 글이나 말로 한 판을 주고받는 개발용 뼈대입니다. 기본은 모의 모델로 돌고, 이 Mac에서 도는 로컬 모델(Ollama)로 띄우면 요금 없이 언어 모델의 답을 받습니다(아래 '로컬 모델로 쓰기(무료)'). 판은 SQLite 파일에 남습니다. 음성은 브라우저에 들어 있는 음성 인식과 음성 합성으로 합니다(아래 '음성'). 서버는 모델에 쓰는 돈과 한 사용자의 하루 턴 수에 상한을 둡니다(아래 '비용 상한'). 요금이 드는 모델은 아직 붙이지 않았고, 붙이는 때는 사용자가 정합니다.

한 판은 이렇게 흐릅니다.

1. 주제를 고릅니다.
2. 두 입장 사이 다섯 칸 척도에서 지금의 생각을 고릅니다. 한쪽으로 기울었으면 그 입장을 지키고, 반반이면 시험해 볼 입장을 고릅니다. 상대는 반대 입장의 캐릭터입니다.
3. 글이나 말로 주고받습니다. 음성을 켜면 말한 것이 글로 바뀌어 입력 칸에 들어가고, 읽어 보고 고친 뒤 직접 보냅니다. 상대의 답은 소리로 읽어 줍니다. 글 입력은 언제나 됩니다.
4. 판이 끝나면(30턴, 또는 끝내기) 같은 척도의 사후 입장과 훈계 문항("이번 판은 토론이었습니까, 훈계였습니까")에 답해야 판이 닫힙니다. '목록으로'로 나간 판은 끝난 것이 아니므로 묻지 않고, 나중에 이어 할 수 있습니다.

## 띄우기

```
npm install
npm run app:dev
```

서버(Hono, `127.0.0.1:8787`)와 화면(Vite)을 함께 띄웁니다. 화면 주소는 실행하면 나옵니다(보통 `http://127.0.0.1:5173/`).

- 기본은 모의 모델입니다. `.env`를 읽지 않으므로 비용이 들지 않습니다. 모의 모델의 답은 흐름을 확인하려고 만든 문장이라 뜻이 없습니다. 로컬 모델로 띄우는 법은 아래 '로컬 모델로 쓰기(무료)'에 있습니다.
- 판의 방식은 `APP_MODE`로 고릅니다. 적지 않으면(`engine`) 모든 판을 엔진 방식으로 합니다. 엔진 방식에서는 턴마다 판정기가 사용자의 말이 상대의 전제를 무너뜨렸는지 먼저 판정하고, 상대가 그 판정에 맞춰 답합니다(판정 실험의 `engine` 조건).
  - 지시문 방식과 견주는 눈가림 사람 비교에는 `APP_MODE=random`을 붙여 띄웁니다. 서버가 판마다 지시문 방식과 엔진 방식 가운데 하나를 반씩 무작위로 고릅니다.
  - `engine`과 `random` 밖의 값이면 까닭을 알리고 띄우지 않습니다.
  - 기본을 엔진 방식으로 둔 것은 개인 사용에서 판의 절반이 지시문 방식이 되지 않게 하려는 것입니다. 반씩 고르던 때 실제 Ollama(`qwen3:8b`, 생각 끔)로 띄운 두 판이 지시문 방식으로 뽑혔고, 두 판 모두 되풀이와 권위 호소의 턴마다 상대가 전제 하나를 거두겠다고 답했습니다. 기록은 아래 '한계'에 적은 폴더의 `real-dev-smoke-002344.txt`와 `real-dev-smoke-004255.txt`입니다(2026-11-23).
- 판은 `data/app.sqlite`에 남아, 다시 띄워도 '지난 판'에서 이어 하거나 다시 볼 수 있습니다. 판에는 토론 기록(개인정보)이 들어 있어 `data/`는 커밋하지 않습니다.
- 다른 파일을 쓰려면 `APP_DB_PATH=경로`를, 파일 없이 메모리에만 두려면 `APP_DB_PATH=:memory:`를 붙여 띄웁니다. `.sqlite` 파일은 어디에 두어도 git이 무시합니다.
- 한 사용자의 하루 턴 수 상한(90턴)은 모의 모델과 로컬 모델에도 걸립니다(아래 '비용 상한'). 턴 수는 판 파일에 저장된 턴으로 세므로, 개발하다 닿으면 다른 파일로 띄웁니다.
- 서버 코드를 고치면 명령을 다시 띄웁니다. 화면 코드는 저장하면 바로 바뀝니다.

화면만 빌드하려면 `npm run app:build`를 씁니다. 결과는 `app/web/dist/`에 생기고 커밋하지 않습니다.

## 로컬 모델로 쓰기(무료)

상대와 판정기를 이 Mac에서 도는 로컬 모델로 돌립니다. 서버는 Ollama가 이 컴퓨터에 여는 OpenAI 호환 주소로 모델을 부릅니다. 모델이 이 컴퓨터 안에서 돌므로 요금이 없습니다.

### 설치(한 번, 직접 합니다)

1. ollama.com의 내려받기 페이지에서 macOS 앱(`Ollama.dmg`)을 받아 응용 프로그램 폴더에 넣고 켭니다. macOS 14(Sonoma) 이상이 필요합니다. 처음 켜면 터미널에서 `ollama` 명령을 쓸 수 있게 링크를 만들지 묻습니다(Ollama 문서 'macOS').
2. 터미널에서 기본 모델을 받습니다. 약 5.2GB입니다(Ollama 모델 페이지 `qwen3:8b`). 받은 모델은 `ollama ls`로 봅니다.

   ```
   ollama pull qwen3:8b
   ```

   다른 모델을 쓰려면 그 모델을 받아 `APP_LOCAL_MODEL`에 적습니다. 예를 들어 `exaone3.5:7.8b`(약 4.8GB)도 쓸 수 있습니다(아래 'EXAONE의 사용 조건').

### 띄우는 명령

```
APP_MODEL=local npm run app:dev
```

- 띄우기 전에 로컬 모델 서버의 모델 목록 둘을 읽습니다. OpenAI 호환 목록(`GET {APP_LOCAL_URL}/models`)으로 서버에 닿는지와 모델이 있는지 보고, Ollama의 목록(`GET /api/tags`)으로 원격 모델인지 봅니다(아래 '무료인 까닭'). 서버에 닿지 못하면 Ollama 앱을 켜라고, 모델이 없으면 받을 명령(`ollama pull <모델>`)을, 원격 모델이면 이 컴퓨터에서 도는 모델을 쓰라고 알리고 띄우지 않습니다. 이 확인은 모델을 부르지 않습니다.
- 서버의 첫 줄이 판의 방식(위 '띄우기'), 모델, 생각하는 역할을 알립니다. 예: `서버: http://127.0.0.1:8787/api (엔진 방식, 로컬 모델 qwen3:8b, 생각: 판정기만, 무료: 이 컴퓨터 안의 주소만, 판 저장: data/app.sqlite)`
- 화면에는 모의 모델 안내가 나오지 않습니다.
- `APP_MODEL`이 없으면 지금처럼 모의 모델로 뜹니다. `mock`과 `local` 밖의 값이면 까닭을 알리고 띄우지 않습니다.

| 환경 변수 | 적지 않으면 | 뜻 |
| --- | --- | --- |
| `APP_MODEL` | `mock` | `mock`은 모의 모델, `local`은 로컬 모델 |
| `APP_LOCAL_URL` | `http://127.0.0.1:11434/v1` | 로컬 모델 서버의 OpenAI 호환 주소. Ollama는 기본으로 127.0.0.1의 11434번 포트에서 듣습니다(Ollama FAQ) |
| `APP_LOCAL_MODEL` | `qwen3:8b` | 상대 모델 |
| `APP_LOCAL_JUDGE_MODEL` | `APP_LOCAL_MODEL`과 같음 | 판정기 모델. 메모리(16GB)에 모델 둘을 함께 올리지 않으려고, 기본은 한 모델을 두 역할이 함께 씁니다 |
| `APP_LOCAL_THINK` | `judge` | 답하기 전에 생각(추론)할 역할. `judge`는 판정기만, `all`은 판정기와 상대가 생각하고, `none`은 둘 다 생각하지 않습니다. 생각하지 않는 역할의 요청에는 `reasoning_effort: "none"`을 보내고, 생각하는 역할의 요청에는 보내지 않아 모델의 기본대로 둡니다. 생각하면 느립니다(아래 '한계'). 그 밖의 값이면 띄우지 않습니다 |

`.env`는 읽지 않고 키도 쓰지 않습니다. Ollama는 OpenAI 호환 요청의 키를 보지 않습니다(Ollama 문서 'OpenAI compatibility').

Ollama는 생각을 켜고 끄기만 하는 모델에서 `reasoning_effort: "none"`을 생각 끔으로 받습니다(같은 문서). `qwen3:8b`에 짧은 인사를 보내 보니, 생각을 끄면 출력 토큰이 10개였고, 켜면 115개였으며 생각(423자)이 답과 따로 왔습니다. `exaone3.5:7.8b`는 이 값을 받아도 그대로 답했습니다(2026-11-22 실측).

기본을 판정기만 생각하게 둔 까닭은 아래 '한계'의 표에 적은 실측입니다. `qwen3:8b` 하나에 두 역할을 맡기고, 엔진 방식으로 판정 실험 q01의 대본을 보냈습니다.

- 두 역할 모두 생각을 끄면 판정기가 되풀이한 1턴을 반론(`argument`)으로 판정했고, 상대가 P1을 거뒀습니다(1~6턴, `cmp-qwen3-8b-engine-none-234635.md`).
- 판정기만 생각하게 두면 압박 12턴에서 엔진이 거둔 전제가 없었습니다(1~14턴, `engine-q01-judge-think-opp-none-074010.md`). 남은 문제는 아래 '한계'에 있습니다.
- 두 역할 모두 생각하게 두면 한 턴이 72~111초였고, 상대가 판정의 분류를 그대로 말했습니다(1~6턴, `cmp-qwen3-8b-engine-234929.md`).

### 무료인 까닭

- 서버는 `APP_LOCAL_URL`이 이 컴퓨터의 주소일 때만 로컬 모델을 붙입니다. http나 https이고 호스트가 `127.0.0.1`, `localhost`, `[::1]` 가운데 하나여야 합니다. 원격 주소, 사설망 주소(`192.168…` 등), `127.0.0.1.example.com` 같은 주소면 띄우지 않고, 그 주소로는 모델 목록도 묻지 않습니다.
- 호스트가 이 컴퓨터여도 `@` 앞에 사용자 정보가 든 주소(`http://이름@127.0.0.1:11434/v1`)는 받지 않습니다. 그런 주소로는 요청을 보낼 수 없어서, 사용자 정보를 빼라고 알리고 띄우지 않습니다.
- 이 검사는 로컬 모델의 출처를 만드는 한 곳(`server/models.ts`의 `localSource`)에만 있습니다. 검사를 거치지 않은 로컬 출처는 만들 수 없습니다.
- 로컬 모델 서버가 다른 주소로 넘기는 응답(redirect)을 주어도 따라가지 않고 그 요청을 실패로 둡니다. 그래서 요청은 검사한 주소 밖으로 나가지 않습니다. 턴에서 넘기면 그 턴이 실패하고 판은 그대로입니다. 띄울 때 확인에서 넘기면 서버에 닿지 못했다고 알리고 띄우지 않습니다.
- 로컬 모델의 단가는 0입니다. 원장에는 호출마다 응답이 알려 준 토큰이 남지만 비용은 0이라, 서비스 비용 상한에 닿지 않습니다.
- Ollama의 클라우드 모델은 쓰지 않습니다. Ollama 문서('Cloud')는 클라우드 모델을 로컬 API로 불러도 추론이 Ollama의 클라우드에서 돈다고 적습니다. 그런 모델을 적으면 서버는 이 컴퓨터의 주소만 부르지만 대화는 이 컴퓨터 밖으로 나갑니다. 클라우드는 ollama.com 계정이 있어야 쓰고, 사용량과 요금제가 따로 있습니다(같은 문서, 'Usage').
  - 띄울 때 Ollama의 목록(`GET /api/tags`)이 두 역할의 모델에 원격 모델의 칸(`remote_host`, `remote_model`)을 적었으면 띄우지 않습니다. Ollama 문서('List models')는 두 칸을 원격 모델일 때 있는 칸으로 적습니다. 클라우드 모델이 이 목록에 그렇게 나오는지는 문서에 없고 확인하지 못했습니다. 이 확인은 띄울 때 한 번만 하고, 이 목록이 없는 서버(Ollama가 아닌 서버)에서는 건너뜁니다.
  - 확실히 막으려면 Ollama의 클라우드 기능을 끕니다. `~/.ollama/server.json`에 `"disable_ollama_cloud": true`를 넣고 Ollama를 다시 켭니다. 환경 변수 `OLLAMA_NO_CLOUD=1`로도 끌 수 있고, macOS 앱에는 환경 변수를 `launchctl setenv`로 줍니다. 꺼지면 Ollama의 서버 기록에 `Ollama cloud disabled: true`가 나옵니다(Ollama FAQ 'How do I disable Ollama's cloud features?', 'How do I configure Ollama server?'). macOS에서 서버 기록은 `~/.ollama/logs/server.log`입니다(Ollama 문서 'Troubleshooting').

### 그대로 걸리는 것

한 사용자의 하루 턴 수(90턴), 한 번에 한 턴, 원장이 닫히면 새 판과 턴을 막는 것은 모의 모델 때와 같이 걸립니다(아래 '비용 상한').

## 음성

음성은 브라우저에 들어 있는 기능만 씁니다. 새 의존성도 음성 서비스 요금도 없습니다. 판 화면의 `[음성으로 하기]`를 눌러야 켜지고, 판을 바꿔도 켜진 채로 남으며, 페이지를 새로 열면 꺼져 있습니다. 글 입력은 음성을 켜도 그대로 됩니다.

음성을 켠 한 턴은 이렇게 흐릅니다.

1. `[말하기]`를 누르고 말합니다. 듣는 동안 지금까지 들은 글이 입력 칸 아래에 보입니다.
2. 말을 마치고 `[말 마치기]`를 누르거나 잠시 기다리면, 인식된 글이 입력 칸 끝에 붙습니다. 한 번에 한 발화만 받고, 여러 번에 나눠 말하면 이어 붙습니다.
3. 글을 읽어 보고 고친 뒤 `[보내기]`를 누릅니다. 자동으로 보내지 않습니다.
4. 상대의 답을 소리로 읽습니다. 말풍선의 `[듣기]`로 다시 듣고 `[멈춤]`으로 끊습니다.

### 소리와 글이 가는 곳

- **이 앱은 소리를 받지 않습니다.** 화면의 코드는 소리를 녹음하지도 서버로 보내지도 않습니다(`getUserMedia`, `MediaRecorder`를 쓰지 않습니다). 서버에는 글만 가고, 음성 원본은 어디에도 저장하지 않습니다.
- **말소리**는 브라우저의 음성 인식(`SpeechRecognition`)이 글로 바꿉니다.
  - 기기 안에서 바꿀 수 있는 브라우저면 그렇게 합니다. 음성을 켤 때 한국어 인식 팩이 없으면 한 번 내려받습니다. 브라우저가 기기 안 인식을 쓸 수 있다고 답하면 화면에 '이 기기 안에서 글로 바뀝니다'라고 알립니다.
  - 브라우저가 쓸 수 있다고 답해도, 인식 팩을 내려받은 그 브라우저 세션에서는 인식이 되지 않았습니다(아래 실측). 그래서 인식 팩을 내려받은 뒤 말소리가 글로 바뀐 적이 없는 동안에는, 화면이 '이 기기 안에서 글로 바뀝니다' 대신 브라우저를 완전히 종료했다가 다시 열라고 알립니다.
    - 인식 팩을 이번에 내려받았는지는 설치에 걸린 시간으로 가립니다. 1초 이상 걸렸으면 내려받은 것으로 봅니다(추정).
    - 그동안에도 `[말하기]`는 누를 수 있습니다. 듣기가 글 없이 끝나면 '말소리를 듣지 못했습니다' 대신 기기 안 음성 인식이 아직 준비되지 않았다고 알립니다.
    - 말소리가 한 번 글로 바뀌면 그 뒤로는 '이 기기 안에서 글로 바뀝니다'라고 알립니다. 브라우저를 다시 연 뒤에도 그때까지는 같은 안내가 보입니다.
  - 브라우저가 쓸 수 있다고 답하지 않으면 브라우저가 정한 방식으로 바뀝니다. 이때는 말소리가 브라우저 회사의 서버로 갈 수 있다고 화면에 알립니다. 페이지는 브라우저가 어디서 인식했는지 알 수 없습니다.
- **읽을 글**은 브라우저의 음성 합성(`speechSynthesis`)이 읽습니다.
  - 기기 안의 한국어 목소리로 읽습니다. 기기 안에 한국어 목소리가 없으면 읽지 않습니다.
  - 브라우저 회사 서버의 목소리(Chrome의 'Google 한국의' 등)는 읽을 글을 그 서버로 보냅니다. 그래서 앱이 스스로 고르지 않고, 사용자가 목록에서 직접 고른 경우에만 씁니다. 목록에는 '(기기 밖)'을 붙이고, 쓰는 동안 화면에 알립니다. 기기 안에 한국어 목소리가 없는 브라우저에서는 고른 뒤에도 목록의 '고르지 않음'으로 되돌릴 수 있고, 되돌리면 읽던 것을 멈추고 저장한 이름을 지웁니다.
  - 목소리 목록은 여러 번에 걸쳐 오고, 다 왔다는 신호가 없습니다. 기기 목소리가 늦게 와도 그사이 읽을 글이 밖으로 나가지 않습니다. 화면은 마지막 변경 뒤 2.5초까지 '찾는 중'이라고 알리고, 그 뒤에는 '없다'고 알립니다(이 2.5초는 추정이고 화면 문구만 가릅니다).
- 이 브라우저의 `localStorage`에만 남기는 것이 둘 있습니다. 고른 목소리의 이름(`dialogos.voice`)과, 인식 팩을 내려받은 뒤 아직 말소리가 글로 바뀐 적이 없다는 표시(`dialogos.pack-pending`)입니다. 표시는 값 하나뿐이고, 말소리가 한 번 글로 바뀌면 지웁니다.

### 듣기와 읽기의 규칙

- 한 번에 한 발화만 받습니다(`continuous = false`). 소리 트랙으로 잰 기기 안 인식은 말이 끝나도 스스로 끝내지 않았습니다(아래 실측). 그래서 브라우저가 끝내 주기를 기다리지 않고 화면이 시간을 재어 마칩니다. 브라우저가 먼저 끝내면 그 결과를 씁니다.
  - 들은 글이 2.5초 동안 달라지지 않으면 인식을 마치고 확정된 글을 받습니다.
  - 듣기 시작하고 10초 동안 아무것도 듣지 못하면 그만둡니다.
  - 마치라고 한 뒤 3초 안에 끝나지 않으면 그때까지 들은 글로 끝냅니다.
  - 세 값은 써 보며 조정할 값입니다(`web/src/listen.ts`).
- 문제가 생기면 종류에 따라 다르게 다룹니다(`web/src/listen.ts`의 표).
  - 마이크가 허용되지 않았거나 없을 때, 브라우저가 음성 인식을 막았을 때, 한국어를 지원하지 않을 때는 그 페이지에서 음성 입력을 끄고 이유를 보입니다. 입력 칸은 그대로 씁니다.
  - 말소리를 듣지 못했거나, 중간에 끊겼거나, 인식 서버에 닿지 못했을 때는 알리기만 하고 다시 누를 수 있습니다.
- 읽을 글은 문장 끝과 줄바꿈에서 나누고, 긴 문장은 80자 안에 들게 쉼표와 공백에서 더 나눕니다. 실측한 속도(초당 약 7.7자)로 80자는 약 10초입니다. 원격 목소리가 15초쯤에서 끊긴다는 보고를 피하려는 길이인데, 그 보고는 직접 재지 않았습니다.
- 두 캐릭터는 속도와 높낮이로 구분합니다. 값은 들어 보고 조정할 값입니다(`web/src/speak.ts`의 표).
- 음성을 켠 채로 판을 열거나 새 답이 오면 그 말을 읽습니다. 끝난 판을 다시 볼 때는 자동으로 읽지 않습니다. 보내기, 말하기, 끝내기, 목록으로, 음성 끄기를 누르면 읽던 것을 끊습니다. 목소리를 바꾸면 다음 읽기부터 그 목소리를 씁니다.
- 읽기 대기열은 문장이 읽히는 중일 때만 끊습니다. Chrome은 넣은 문장이 시작하기 전에 대기열을 끊으면 대기열이 멈출 수 있고, 그러면 그 뒤에 넣은 문장을 읽지 않습니다(아래 실측).
  - 넣었지만 아직 시작 전이거나 문장과 문장 사이면 끊지 않고 기다렸다가, 다음 문장이 시작할 때 끊습니다. 새로 읽을 말이 있으면 그때 넣습니다. 문장 사이(앞 문장의 끝 이벤트 안)에 끊었을 때는 세 번 모두 멈추지 않았지만, 경우를 나누지 않고 같은 규칙으로 다룹니다.
  - 넣은 문장이 6초 동안 시작하지도 끝나지도 않으면 대기열이 멈춘 것으로 보고 대기열을 비웁니다. 읽으려던 말이 있었으면 읽는 중에 문제가 생겼다고 알립니다. 넣은 뒤 시작까지는 보통 25ms 안이었고, 음성을 처음 켠 직후에는 약 1.1초였습니다. 6초는 그보다 넉넉히 잡은 값입니다(`web/src/speak.ts`).
- 듣는 중에 음성을 끄면 그때까지 들은 글을 입력 칸에 넣습니다. 듣는 중에 판을 끝내거나 목록으로 나가면 듣던 것은 버립니다.
- 듣는 동안 바뀌는 글과 안내는 화면 낭독기가 읽지 않게 두었고, 앱이 상대의 말을 읽는 동안에는 대화 목록의 새 말 알림을 끕니다. 낭독 소리가 마이크로 들어가거나 같은 말이 겹쳐 읽히지 않게 하려는 것입니다.

### 고친 턴 세기

확정된 기준은 "고쳐야 하는 턴이 5턴 중 1턴을 넘으면 음성 인식을 올린다"입니다. 이것을 잴 수 있게 턴마다 말을 넣은 방식(`input`)을 서버에 남깁니다.

| `input` | 뜻 |
| --- | --- |
| `text` | 글로 넣었습니다 |
| `voice` | 음성 인식이 적은 글 그대로 보냈습니다 |
| `voice-edited` | 인식된 글을 고쳐서 보냈습니다 |

- 넣은 방식은 화면이 보낼 때 정합니다(`web/src/dictation.ts`). 그 턴에 인식되어 입력 칸에 들어간 조각이 모두, 들어간 차례대로, 보낼 글 안에 그대로 남아 있으면 `voice`이고 아니면 `voice-edited`입니다. 글자와 숫자만 견줍니다.
  - 공백과 문장 부호만 손본 턴은 고친 턴이 아닙니다. 인식된 한국어 글에는 문장 부호가 원래 없습니다.
  - 인식된 글을 둔 채 앞뒤에 글로 덧붙인 것, 여러 번에 나눠 말한 것도 고친 턴이 아닙니다.
  - 낱말을 고쳤거나, 인식된 글을 지우고 다시 썼거나, 조각의 차례를 바꿨으면 고친 턴입니다.
- 판과 지난 판 목록에는 `voice: { turns, edited }`가 실립니다. 말로 넣은 턴의 수와 그 가운데 고쳐 보낸 턴의 수입니다. 말로 넣은 턴이 있는 판은 지난 판 목록과 기록을 남긴 끝 화면에 한 줄로 보입니다.

이 셈의 한계는 다음과 같습니다.

- 고친 까닭은 모릅니다. 인식이 틀려서 고친 것과, 말한 뒤 생각이 바뀌어 고친 것을 가리지 못합니다.
- 한 마디만 말하고 나머지를 글로 쓴 턴도 '말로 넣은 턴'에 들어갑니다. 이런 턴이 많으면 고친 턴의 비율이 낮게 나옵니다.
- 인식된 글을 지웠어도, 직접 쓴 글에 같은 글자가 차례대로 들어 있으면 고친 턴으로 세지 못합니다(예: '생각'이 인식됐는데 지우고 '저는 그렇게 생각하지 않습니다'라고 쓴 경우).
- 인식에 실패해 글이 하나도 들어오지 않은 턴은 글로 넣은 턴이 됩니다. 실패한 듣기의 횟수는 남기지 않습니다.
- 틀리게 인식된 글을 고치지 않고 보낸 턴은 고친 턴으로 세지 않습니다. 그래서 '고쳐야 하는 턴'보다 적게 셀 수 있습니다.
- 띄어쓰기와 문장 부호를 손본 수고는 세지 않습니다.
- 넣은 방식은 화면이 알려 준 값입니다. 서버는 세 값 가운데 하나인지만 확인합니다.
- 음성을 붙이기 전에 저장한 턴은 모두 `text`입니다.

### 확인한 것과 확인하지 못한 것

아래는 2026-11-21과 22에 macOS 26의 Chrome 157에서 잰 것입니다. 다른 브라우저의 동작은 여기서 추정하지 않습니다.

| 확인한 것 | 결과 |
| --- | --- |
| 기기 안 인식의 준비 | 설치 전에는 쓸 수 있는지 물으면 `downloadable`입니다. 사용자의 누름 없이 설치를 부르면 거절됩니다. 누름 안에서 부르면 새 사용자 폴더에서 6.6초 뒤에 끝났고, 한국어 팩 54MB와 인식 엔진 25MB를 내려받았습니다(한국어만 설치했을 때. 그 세션에서는 60초 뒤에도 다른 언어 팩은 생기지 않았습니다) |
| 인식 팩을 내려받았는지 | 설치에 걸린 시간이 갈랐습니다. 새 사용자 폴더에서는 6.1~9.4초가 걸렸고(출력을 남긴 네 번), 인식 팩이 이미 있는 폴더에서는 약 2ms 만에 끝났습니다(두 번). 쓸 수 있는지 묻는 답은 가르지 못했습니다. 인식 팩이 이미 있는 폴더에서도 Chrome을 띄운 지 약 3초 뒤에 물으면 `downloadable`이었습니다(두 폴더. 그 뒤 설치는 약 2ms 만에 끝났고 다시 물으면 `available`) |
| 인식 팩을 내려받은 세션의 인식 | 인식 팩을 내려받은 그 브라우저 세션에서는 기기 안 인식이 되지 않았습니다(새 사용자 폴더 다섯 개 모두. 준비 직후, 29초 뒤, 59초 뒤, 페이지를 새로 연 뒤). 쓸 수 있는지 물으면 `available`이었지만 Chrome의 인식 프로세스가 뜨지 않았습니다. 마이크 경로(가짜 장치)의 듣기는 시작 이벤트가 3~8ms에 오고, 결과 없이 8.2~8.3초에 `no-speech` 오류와 끝 이벤트가 왔습니다. 소리 트랙으로 넣은 듣기는 시작 이벤트 없이 0.2초 안에 `aborted` 오류와 끝 이벤트가 왔고(여섯 번), 한 번은 30초 동안 아무 이벤트도 없었습니다 |
| 브라우저를 다시 띄운 직후의 인식 | 같은 사용자 폴더로 Chrome을 다시 띄운 직후에도 잠시 같은 때가 있었습니다(마이크 경로는 시작 이벤트 뒤에 결과가 없고, 소리 트랙 경로는 시작 이벤트 없이 `aborted`). 길게는 약 20초 뒤에 인식이 됐습니다(한 번 봄). 띄우고 약 8초 뒤의 첫 시도부터 된 때도 있었습니다 |
| 내려받은 크기(한 번 잼) | 인식 팩을 내려받은 세션이 네트워크로 받은 것은 46MB였습니다(6.1MB와 40.2MB). 다시 띄운 세션에서는 Chrome이 구성 요소 하나(141MB)를 더 받았고, 그 뒤 사용자 폴더에 `en-US` 팩이 생겼습니다. 이 내려받기가 음성 인식 때문인지는 확인하지 못했습니다 |
| 기기 안 인식의 결과 | 중간 결과가 0.1~0.3초마다 옵니다. 소리 트랙으로 넣은 실측에서는 말이 끝나도 스스로 확정하지 않았습니다(22초를 기다려도 확정 결과와 끝 이벤트가 없었습니다). 실제 마이크에서도 그런지는 확인하지 못했습니다. `stop()`을 부르면 확정 결과와 끝 이벤트가 바로 옵니다. 인식된 글에 문장 부호는 없습니다 |
| 인식기가 멈춘 경우 | 탐색 초기의 네 번은 인식이 시작됐다는 이벤트 뒤로 40초 동안 아무 이벤트도 오지 않았습니다(오류도 끝 이벤트도 없음). 원인은 확인하지 못했고, 같은 조건으로 다시 했을 때는 재현되지 않았습니다. 화면은 이런 경우에 시간 제한으로 빠져나옵니다(인식기를 멈춘 것처럼 바꿔 놓고 확인: 13초 뒤 끝남) |
| 소리는 오는데 말이 없을 때 | 가짜 마이크의 신호음만 들려주면, 8.3초 뒤 브라우저가 `no-speech` 오류와 끝 이벤트를 냈습니다 |
| 목소리 목록 | 처음에는 비어 있습니다. 6ms 뒤에는 원격 목소리 19개만 있고, 약 1.1초 뒤에 기기 목소리 180개가 더해집니다. 한국어는 기기 목소리 9개(자연스러운 것은 Yuna)와 원격 목소리 1개('Google 한국의')입니다 |
| 목소리를 정하지 않은 읽기 | 목소리 목록은 원격 목소리 19개가 먼저 오고, 기기 목소리는 약 1.1초 뒤에 옵니다(위 줄). 목소리를 정하지 않으면 브라우저가 고르며, 그때는 원격 목소리일 수 있습니다(추정). 그래서 읽을 때마다 고른 목소리를 넣습니다 |
| 사용자의 누름 없는 첫 읽기 | `not-allowed`로 막힙니다. 누름 안에서 한 번 읽은 뒤로는 누름 없이도 됩니다 |
| 읽기 끊기 | 읽던 문장만 `interrupted`를 내고, 대기 중이던 문장은 아무 이벤트도 내지 않습니다. 맨 앞 문장이 시작(`start` 이벤트)하기 전에 끊으면 대기열이 멈출 수 있습니다. 끊고 300ms 뒤에 넣은 세 문장이 하나도 시작하지 않았고 `speaking`과 `pending`이 참으로 남았습니다(창 없는 Chrome 세 번, 창 있는 Chrome 한 번). 문장을 하나만 넣었을 때도, 넣기 전에 한 번 더 끊었을 때도 같았습니다. 빈 글은 시작 전에 끊어도 멈추지 않았습니다. 시작한 뒤(`start` 이벤트 안, 그 뒤 30~500ms)에 끊으면 뒤에 넣은 문장이 모두 읽혔습니다. 멈춘 대기열은 끊고 같은 틱에 다시 넣었을 때 두 번 가운데 한 번 되살아났습니다. 그래서 앱은 문장이 읽히는 중일 때만 끊습니다 |
| 긴 글과 속도 | 186자를 기기 목소리(Yuna, 속도 1)로 한 번에 읽는 데 24.2초가 걸렸고 끊기지 않았습니다. 속도 값은 읽는 시간을 실제로 바꿉니다(같은 문장이 0.8에서 6.2초, 1.2에서 4.5초) |

확인하지 못한 것은 다음과 같습니다.

- **실제 마이크로 하는 인식.** 실제 마이크는 쓰지 않았습니다. 인식은 소리 트랙을 인식기에 넘기는 방식으로 쟀고, 마이크 경로는 가짜 장치로만 봤습니다. 실제 마이크로 듣는 흐름과 인식의 정확도는 본인 사용에서 확인합니다.
- **인식 팩을 내려받은 세션에서 실제 마이크로 말했을 때.** 그 세션의 마이크 경로는 가짜 장치의 신호음으로만 쟀습니다. 실제 말소리를 넣었을 때의 동작은 확인하지 못했습니다.
- **인식 팩을 내려받은 뒤 브라우저를 종료하지 않고 오래 둔 경우.** 시간을 정해 본 것은 내려받은 뒤 59초까지입니다. 더 오래 두면 인식이 되는지는 확인하지 못했습니다.
- **Safari와 iOS, Android, Edge, Firefox.** 돌려 보지 않았습니다. 기기 안 인식을 확인할 수 없는 브라우저에서는 화면이 '브라우저가 정한 방식'이라고만 알립니다. 첫 읽기를 사용자의 누름 안에서 하는 처리와, 읽는 것이 없을 때는 읽기 대기열을 끊지 않는 처리는 Safari와 iOS를 염두에 둔 것인데, 그 브라우저에서 확인하지 못했습니다.
- **원격 목소리로 읽는 긴 글.** 15초쯤에서 끊긴다는 보고는 직접 재지 않았습니다.
- **화면 낭독기와 함께 쓰는 흐름.** 돌려 보지 않았습니다. 낭독기를 스피커로 들으면 단추 이름을 읽는 소리가 인식에 섞일 수 있습니다.
- **마이크 허락 창.** 창이 실제로 뜨는 흐름을 보지 못했습니다. 명세대로라면 인식기는 허락한 뒤에 시작을 알리고, 화면은 그때부터 첫 결과 10초를 다시 잽니다. 그렇지 않은 브라우저에서는 늦게 허락했을 때 '말소리를 듣지 못했습니다'가 보이고, 다시 누르면 됩니다.
- **인식 팩 설치가 끝나지 않는 경우.** 시간 제한을 두지 않았습니다. 그동안 `[말하기]`는 막히고 글 입력은 됩니다.
- **목소리 이름.** 고품질판 유나와 Windows의 한국어 목소리 이름은 직접 보지 못하고 차례 표에 넣었습니다.

## 비용 상한

서버가 모델에 쓰는 돈과 한 사용자가 쓰는 양에 상한을 둡니다(`server/budget.ts`). 실제 모델을 붙이기 전에 갖춘 장치입니다. 지금은 모의 모델과 로컬 모델만 써서 원장에 남는 돈은 0원이고(로컬 모델은 토큰만 남고 비용은 0), 실제로 걸리는 것은 하루 턴 수와 한 번에 한 턴입니다.

| 상한 | 값 | 닿으면 |
| --- | --- | --- |
| 서비스 전체가 모델에 쓰는 돈 | 100,000원(약 74.85달러) | 새 판과 턴을 503으로 막습니다. 원장의 합은 줄지 않으므로 사람이 값을 올릴 때까지 막습니다 |
| 한 사용자의 하루 턴 수 | 90턴(30턴 판 세 개) | 새 판과 턴을 429로 막습니다. 한국 시간 0시부터 다시 받습니다 |
| 한 사용자가 한 번에 보내는 턴 | 1턴 | 다른 판에 보낸 턴의 답을 기다리는 동안 온 턴을 409로 막습니다 |

두 값(100,000원, 90턴)은 제안값이고 사용자가 정합니다(`LIMITS`). 원은 1달러 1,336원으로 바꿉니다. 비용을 추정할 때 가정한 환율(2026-11-17)이고, 실제 환율을 따라가지 않습니다.

### 원장

- 실제 모델을 한 번 부를 때마다, 응답을 하나라도 받았으면 그 호출의 시각, 사용자, 판, 역할, 모델 이름, 응답을 받은 호출 수, 입력 토큰, 과금되는 출력 토큰, 비용을 SQLite의 `spend` 표에 한 줄 덧붙입니다. 고치거나 지우지 않고, 판이 없어져도 남습니다. 서비스 상한은 이 표에 처음부터 쌓인 합으로 셉니다.
- 비용은 입력 토큰 × 입력 단가 + 과금되는 출력 토큰 × 출력 단가입니다. 단가는 공식 가격표처럼 100만 토큰당 달러로 두고, 비용은 100만분의 1달러 단위로 올림해 정수로 남깁니다.
- 과금되는 출력 토큰은 응답이 전체 토큰을 알려 주면 전체에서 입력을 뺀 값(생각 토큰 포함)이고, 아니면 출력 토큰입니다. 판정 실험의 점검 절과 같은 셈입니다(`eval/src/util.ts`의 `billedOutputTokens`).
- 부를 때마다 새 모델을 만들어, 그 모델이 센 양을 그 호출 하나의 양으로 남깁니다. 여러 판이 한 모델의 사용량을 함께 쓰지 않습니다.
- 호출이 끝내 실패해도 받은 응답의 양은 남깁니다. 판정기는 답했는데 상대가 실패한 턴도 판정기의 양은 남습니다.
- 원장에 남기지 못하면 그 턴은 실패합니다. 모르는 비용으로 진행하지 않으려는 것입니다.
  - 그 뒤로는 서버를 다시 띄울 때까지 새 판과 턴을 503으로 막습니다(원장이 닫힙니다). 남기지 못한 호출의 양이 빠진 원장 합으로는 서비스 상한을 셀 수 없기 때문입니다. 원장이 닫힐 때 서버 기록에 한 줄을 남깁니다.
  - 남기지 못한 호출의 양은 원장에 없으므로, 다시 띄우기 전에 제공사의 사용량과 원장을 맞춰 봅니다.
  - 원장 쓰기가 실패했을 때만 닫습니다. 모델 호출이 실패한 요청과, 상한을 확인하다 원장을 읽지 못한 요청은 그 요청만 실패합니다.
- 모의 모델은 돈이 들지 않아 원장에 남기지 않습니다. 로컬 모델은 원장에 남기되 단가가 0이라 비용이 0입니다(위 '로컬 모델로 쓰기(무료)').

### 확인하는 때와 차례

- 판 시작과 한 턴에서 확인합니다. 끝내기와 끝 기록은 모델을 부르지 않아 막지 않습니다.
- 잘못된 요청(400, 404, 409)을 먼저 막고 상한은 그 뒤에 봅니다. 없는 판에 보낸 턴은 상한에 닿았어도 404입니다.
- 원장이 닫혔는지(503)를 가장 먼저 보고, 서비스 상한(503), 하루 턴 수(429) 차례로 봅니다. 원장이 닫혔으면 원장을 읽지 않아, 저장소가 아직 망가져 있어도 막는 까닭을 알립니다. 503을 429보다 먼저 보는 것은 서비스가 멈췄는데 내일 다시 할 수 있다고 알리지 않으려는 것입니다.
- 하루 턴 수는 한국 시간 그날 0시 이후에 저장된 그 사용자의 턴을 셉니다. 판이 달라도 함께 세고, 모의 모델의 턴도 셉니다. 모델이 실패해 저장되지 않은 턴은 세지 않습니다.
- 상한은 턴을 시작할 때 확인합니다. 그래서 상한을 넘는 양은 그때 진행 중이던 턴의 비용까지입니다. 사용자마다 한 번에 한 턴만 처리하므로 넘는 양은 사용자마다 많아야 한 턴이고, 하루 턴 수는 넘지 않습니다. 사용자의 턴 자리는 상한 확인부터 턴 저장까지 잡습니다.
- 원장이 닫혀도 닫히기 전에 상한 확인을 시작한 턴은 막지 않습니다. 그래서 기록 없이 나가는 양도 사용자마다 그때 진행 중이던 한 턴까지입니다.
- 거절한 요청은 판을 바꾸지 않고 모델을 부르지 않습니다.
- 판 시작이 막히면 서버의 말을 보입니다. 턴이 막히면 보낸 말을 입력 칸으로 되돌리고 서버의 말을 보이며, 503이면 판을 다시 불러 본 뒤 같은 처리를 합니다(`web/src/turn-flow.ts`). 이 화면 동작은 macOS 26의 Chrome 157(창 없이, 화면 900×1200)에서 개발 서버와 모의 모델로 확인했습니다. 하루 턴 상한(429)과 서비스 상한(503, 검증용 판 파일의 원장에 큰 금액 한 줄을 넣어 만듦)에서 각각, 판 화면의 턴이 막히면 보낸 말이 입력 칸으로 돌아오고 대화와 턴 수가 그대로였으며 거절 메시지가 스크롤 없이 보였습니다. 시작 화면에서 판 시작이 막히면 시작 화면에 머문 채 메시지가 보였습니다. 409(다른 판의 턴)는 모의 모델이 바로 답해 화면에서 만들지 못했고, 확인하지 않았습니다.

### 한계

- 원장에 남는 것은 응답이 알려 준 양입니다. 시간 초과로 끊긴 호출은 제공사가 청구해도 남지 않습니다. 서버가 모델을 부르는 중에 죽으면 그 호출의 양도 남지 않습니다.
- 실제 제공사의 응답이 사용량을 알려 주는지는 확인하지 않았습니다. 검사는 판정 실험의 연결 코드(`eval/src/providers/api.ts`)에 가짜 응답을 넣어 했습니다.
- 사용자의 턴 자리, 같은 판의 잠금, 원장의 닫힘은 서버 하나 안에서만 지켜집니다. 서버를 여럿 띄우면 위의 '사용자마다 많아야 한 턴'과 하루 턴 수가 지켜지지 않을 수 있고, 한 서버의 원장이 닫혀도 다른 서버는 판과 턴을 받습니다. 배포할 때 저장소에서 다시 지킵니다.
- 분당 요청 수 같은 일반 요청 제한은 없습니다. 남은 턴 수는 화면에 보이지 않습니다.
- 실제 모델의 단가 표는 아직 없습니다. 붙일 때 공식 가격표에서 확인해 넣습니다.

## 지키는 것

- **잰 상대와 배포한 상대가 같습니다.** 지시문과 판정은 `eval/src`의 코드를 불러 씁니다. 한 턴은 판정 실험과 같은 `runTurn`(`eval/src/dialogue.ts`)이 맡습니다.
- **방식을 화면에 보내지 않습니다.** 개발 서버는 기본으로 모든 판을 엔진 방식으로 합니다. 눈가림 사람 비교는 `APP_MODE=random`으로 띄워, 서버가 판마다 지시문 방식과 엔진 방식을 반씩 고르게 합니다. 어느 쪽이든 방식과 판정과 장부를 화면에 보내지 않습니다. 사람 비교에서 어느 쪽인지 모른 채 토론하게 하려는 것입니다.
- **키는 서버에만 둡니다.** 화면은 모델을 직접 부르지 않습니다. 지금은 요금이 드는 모델 연결이 없고, 로컬 모델은 키 없이 이 컴퓨터 안의 주소로만 부릅니다. 화면 쪽 환경 변수(`VITE_`로 시작)는 빌드 결과에 들어가므로 비밀값을 넣지 않습니다.
- **소리는 서버에 오지 않습니다.** 말소리는 브라우저에서 글로 바뀌고, 서버는 글과 그 글을 넣은 방식만 받습니다. 음성 원본은 저장하지 않습니다(위 '음성').
- **이 컴퓨터 안에서만 열립니다.** 서버와 화면 모두 127.0.0.1에만 열립니다.
  - 서버는 허용한 주소(Host)로 온 요청만 받습니다. 악성 사이트가 자기 주소를 127.0.0.1로 바꿔 부르는 공격(DNS 리바인딩)을 막으려는 것입니다.
  - 화면 개발 서버는 화면 폴더와 라이브러리 밖의 파일(개인 메모 등)을 내주지 않습니다.
- **배포 전에 할 것.** 이 뼈대는 개발용이라, 배포(3주 차) 전에 다음을 더합니다.
  - 로그인. 판을 사용자별로 나누는 것은 되어 있고, 사람을 가리는 부분(`userOf`)만 남았습니다
  - 분당 요청 수 같은 일반 요청 제한. 비용 상한과 사용자별 하루 턴 수는 되어 있습니다(위 '비용 상한')
  - 여러 서버에서의 잠금. 같은 판의 요청, 사용자의 턴 자리, 원장의 닫힘은 서버 하나 안에서만 지켜지므로, 배포 저장소에서 다시 지킵니다
  - 배포 주소의 허용 목록
  - 보안 헤더

## 주소

| 요청 | 하는 일 |
| --- | --- |
| `GET /api/topics` | 주제 목록과 모델 종류(모의 모델인지) |
| `GET /api/games` | 지난 판 목록(최근 20판). 판마다 `voice`가 실립니다 |
| `POST /api/games` `{ topicId, side, lean }` | 판 시작. `side`는 지킬 입장(0, 1), `lean`은 지금의 생각(-2~2, 음수가 `sides[0]` 쪽)입니다. 사용자의 첫 말과 상대의 첫 발언이 옵니다. 서비스의 비용 상한에 닿았거나 원장이 닫혔으면(위 '원장') 503, 하루 턴 수를 다 썼으면 429입니다 |
| `GET /api/games/:id` | 판 다시 불러오기. `voice`가 실립니다 |
| `POST /api/games/:id/turns` `{ text, input }` | 한 턴. 상대의 답이 옵니다. `input`은 말을 넣은 방식(`text`, `voice`, `voice-edited`)이고, 없으면 `text`입니다. 다른 판에 보낸 턴의 답을 기다리는 중이면 409, 서비스의 비용 상한에 닿았거나 원장이 닫혔으면 503, 하루 턴 수를 다 썼으면 429입니다 |
| `POST /api/games/:id/end` | 판 끝내기 |
| `POST /api/games/:id/record` `{ lean, verdict }` | 끝난 판의 기록. 사후 입장(-2~2)과 훈계 문항의 답(`debate`, `lecture`)을 한 번만 받습니다 |

- 한 판은 30턴(판정 실험이 잰 길이)까지, 한 턴은 1,000자까지 받습니다.
- 판에는 지킨 입장, 시작할 때의 생각, 끝난 방식(30턴, 끝내기), 끝 기록(사후 입장, 훈계 문항의 답)이 남습니다. 끝 기록은 끝난 판에만 한 번 남기고 바꾸지 않습니다.
- 턴마다 말을 넣은 방식(`input`)이 남습니다. 판과 지난 판 목록의 `voice`는 `{ turns, edited }`로, 말로 넣은 턴의 수와 그 가운데 고쳐 보낸 턴의 수입니다(위 '고친 턴 세기'). `input`이 세 값이 아니면 400으로 막습니다. 넣은 방식은 턴에만 남기고 상대와 판정기에게는 보내지 않습니다.
- 생각이 기운 쪽과 지킬 입장이 다르거나, 그 입장의 상대가 아직 없으면 판을 시작하지 않습니다.
- 쓰는 요청은 JSON(`content-type: application/json`)으로만 받습니다. 다른 사이트가 브라우저로 보내는 단순 요청을 막으려는 것입니다.
- 같은 판의 턴과 끝내기는 한 번에 하나씩 처리하고, 처리 중에 온 요청은 409로 막습니다. 서버가 하나일 때만 지켜지므로, 배포할 때 저장소에서 다시 지킵니다.
- 한 사용자의 턴은 판이 달라도 한 번에 하나씩 처리하고, 다른 판에 보낸 턴의 답을 기다리는 동안 온 턴은 409로 막습니다. 이것도 서버가 하나일 때만 지켜집니다(위 '비용 상한').
- 판마다 사용자가 있고, 남의 판은 보기, 턴, 끝내기 모두 '없는 판'(404)으로 답합니다. 로그인을 붙이기 전에는 사용자가 하나(`local`)뿐입니다.
- 메모리 저장소는 판이 1,000개를 넘으면 가장 먼저 만든 판부터 지웁니다.
